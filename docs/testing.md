## CUDA/OpenCL verification boundary

The development container has no real NVIDIA CUDA device/NVRTC and no usable OpenCL GPU platform, so its CUDA/OpenCL checks are deliberately limited to ABI, selection/fallback, CPU-equivalence machinery and exact shipped kernel syntax. Physical device execution is certified separately on the Windows hardware gate and must never be inferred from container syntax checks alone.

CUDA FDTD and CUDA rays each run a mandatory first-use device-vs-CPU validation before they are trusted; OpenCL has equivalent validation. A mismatch or device/compiler exception disables only that backend for the session. The tracked release candidate has passed real NVIDIA CUDA-FDTD and CUDA-ray execution with zero backend failures; runtime diagnostics still expose availability, solve/trace count, failure count, duration and validation description so future hardware can fail closed.

The Windows harness additionally records NVIDIA GPU/driver information and performs a best-effort, hash-pinned NVRTC bootstrap only when an NVIDIA adapter is present. The downloaded NVIDIA binaries are not bundled in the release.

Debug logging also emits compact **explosion path diagnostics** after a full shader solve (`cells`, exact occupied `thickness`, low/high-band transmission, diffraction availability). This makes the next real-client report able to distinguish “sound crossed a thin pane/wall” from “sound reached the listener mainly through an open/diffracted path” without adding per-ray spam for ordinary sources.

Physical hardware validation has exercised the real CUDA Driver/NVRTC ray backend and the strict CUDA-FDTD path on NVIDIA hardware with `self-test=pass` and zero backend failures. These results certify the tracked release behavior; the runtime still performs first-use equivalence checks on every new machine and falls back safely when a driver/device cannot reproduce the CPU reference.

The Windows installer now has an explicit **CUDA FDTD hardware mode**: run it with `-CudaFdtdHardwareGate`. That mode writes `profile=MAXIMUM`, `option.COMPUTE_BACKEND=CUDA`, and deliberately forces `option.RAY_COMPUTE_BACKEND=CPU_PARALLEL` so previously proven CUDA ray activity cannot satisfy the missing wave-compute proof. The session remains an ordinary real-client test: load a normal AIR-dominant world, allow progressive capture to converge, trigger a spatial source such as TNT, keep the world running for roughly 30 seconds, then exit normally. `RESULT.txt` reports `CudaFdtdHardwareGatePassed=True` only when a **wave** diagnostic contains `cuda avail=true`, a positive FDTD `solves` count, `failures=0`, and `self-test=pass`. CPU/OpenCL fallback, CUDA rays with zero FDTD solves, or a CUDA runtime/self-test failure all remain FAIL for this dedicated gate.

The automated loaded-world TNT probe also has an optional strict CUDA-FDTD mode for environments where the real NVIDIA driver is visible to the test process. `./dev-winlab-real-cuda-fdtd-hardware.sh` is the convenience entry point; underneath it the launcher uses `ACOUSTIC_CLIENT_PROFILE=MAXIMUM`, `ACOUSTIC_CLIENT_COMPUTE_BACKEND=CUDA`, `ACOUSTIC_CLIENT_RAY_COMPUTE_BACKEND=CPU_PARALLEL`, and `ACOUSTIC_CLIENT_REQUIRE_CUDA_FDTD=1`. In that mode the probe waits for the Acoustic Shaders scene bootstrap to finish before spawning vanilla TNT and emits `ACOUSTIC-REAL-CUDA-FDTD-OK` only after reflecting the registered production `cuda` FDTD backend and observing `available=true`, `solveCount>0`, `failureCount=0`, and `self-test=pass`. This mode is intentionally not run in the development container because it has no NVIDIA CUDA device/NVRTC.

## Real-client history

Earlier real tests found issues that contract tests could not: Mixin annotation retention, MCP/SRG GUI linkage, footer overlap, a wrong FontRenderer overload and an over-wet outdoor heuristic. Each now has a local regression. This history is why the project continues to distinguish “locally verified” from “real-client certified”.

### Local RFG reobf-equivalent contract

When official Minecraft 1.12.2, MCPConfig, and Forge 14.23.5.2864 binaries are available,
`dev-rfg-reobf-equivalent-contract.sh` assembles the already verified portable + real-SRG production
classfiles, removes only the deterministic-builder compatibility aliases required by the temporary MCP/RFG
source view, and applies the same GUI-method-table and official-SRG member-reference audits used around the
RFG release gate. The resulting audit JAR must contain **exactly the same production class set** as the
verified output, preserve `MixinConfigs` and required projectile/diagnostic/audio resources, remain Java 8,
and avoid shading Kotlin. This is intentionally **not** accepted as proof that Gradle/RFG itself ran;
formal RFG provenance still requires `rfgReleaseGate`.

### Offline local RFG runner

`dev-rfg-local-runner.sh` is the canonical no-network entry point for formal local RFG provenance.
It accepts only an already present exact Gradle 8.14.3 distribution, clean RetroFuturaGradle 1.4.9
checkout at commit `94702da47e2c0d626986a42bd8124c63e52afc2a`, exact Kotlin 2.4.0, bootstrap
JDK 17, official Minecraft/MCPConfig/Forge 2864 artifacts and an imported Gradle/RFG dependency cache.
The offline cache must also contain a discoverable Java 8 toolchain under `GRADLE_USER_HOME/jdks`, because
the pinned RFG workspace compiles/runs the Minecraft side on Java 8 even though Gradle itself runs on 17.
The runner always invokes Gradle with `--offline`; missing cache entries are reported rather than downloaded.
`--preflight-only` validates this complete environment without starting Gradle tasks.

`dev-rfg-buildenv-pack.sh` and `dev-rfg-buildenv-import.sh` define the transferable offline environment
format. The packer requires the official `gradle-8.14.3-bin.zip` SHA-256
`bd71102213493060956ec229d946beee57158dbd89d0e62b91bca0fa2c5f3531`, emits the exact RFG commit as a
Git bundle, and copies only the dependency store (`caches/modules-2`), RFG Minecraft/Fernflower cache
(`caches/retro_futura_gradle`) and Gradle-managed Java toolchains (`jdks`). Every payload file/symlink is
covered by `MANIFEST.tsv`; the importer verifies that manifest and all pinned metadata before reconstructing
the local environment and executing the runner's preflight. `dev-rfg-buildenv-contract.sh` is part of
`dev-verify.sh` and includes a tamper-detection regression for the payload manifest.

`dev-rfg-local-runner-contract.sh` is also part of `dev-verify.sh` and forbids network download commands in
the local runner. A successful normal invocation executes the real `rfgReleaseGate`; the separate
reobf-equivalent contract remains only a bytecode/content safety check and is not provenance.
